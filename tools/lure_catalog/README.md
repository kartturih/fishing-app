# Lure Catalog Build Pipeline

Developer-run, offline data-authoring tool for the Lure Catalog (MFS-028 /
TD-028). Produces `assets/lure_catalog/catalog_v1.json`, the single bundled
asset the application reads at runtime through `LureCatalogAssetLoader` —
entirely offline, with no network access anywhere in this pipeline or in
the running app.

**This tool is never run by the app, by `flutter analyze`/`flutter test`,
or by CI.** It is a plain Python script, run by hand on a developer machine
whenever catalog content is added or corrected — exactly the same shape as
the sibling `tools/syke_bathymetry/` pipeline.

## Requirements

Python 3 standard library only — no third-party packages (see
`requirements.txt`).

## Usage

```bash
cd tools/lure_catalog
python build_catalog.py validate   # run every validation rule; write nothing
python build_catalog.py build      # validate, then write catalog_v1.json
python build_catalog.py check      # rebuild in-memory, diff against the committed asset
python build_catalog.py new-id     # print one fresh UUID v4 for pasting into a source file
```

## Authoring workflow

1. Add a new manufacturer file under `assets/lure_catalog/source/<name>.json`,
   or edit an existing one (see [Source file schema](#source-file-schema)
   below).
2. For any new model/variant, generate a fresh id with
   `python build_catalog.py new-id` and paste it into the `id` field. Never
   reuse an existing id for different content — see
   [Stable IDs](#stable-ids) below.
3. Run `python build_catalog.py validate` and fix every reported issue.
4. Run `python build_catalog.py build`, which re-validates and writes
   `assets/lure_catalog/catalog_v1.json`.
5. Review the diff of `catalog_v1.json` in version control — deterministic,
   stable-sorted output means the diff shows only the intended content
   change (aside from the `generatedAt` timestamp, which always differs
   between runs and carries no meaning of its own).
6. Run `flutter test` from the repository root — the committed-asset
   self-consistency tests catch a corrupted or half-built asset.
7. Launch the app; the runtime importer (`ensureSeeded()`) reconciles the
   new `catalogVersion` the next time the catalog is opened.

A developer adding or correcting catalog content never needs to touch
`LureCatalogRepository`, `LureCatalogMapper`, either Drift table class, any
presentation widget, or any Dart seed list.

## Source file schema

One JSON object per manufacturer file, e.g. `rapala.json`:

```json
{
  "manufacturer": "Rapala",
  "models": [
    {
      "id": "3149d765-a567-49ec-994b-74179d3171c1",
      "modelName": "X-Rap Shad XRS08",
      "productFamily": "X-Rap",
      "lureType": "crankbait",
      "defaultImageReference": "assets/lure_catalog/placeholder_crankbait.png",
      "variants": [
        {
          "id": "442e3a0c-a3f2-49cf-9e8f-751adff94b02",
          "colorName": "Hot Craw",
          "manufacturerColorCode": "HCC",
          "lengthMillimeters": 80,
          "weightGrams": 12,
          "minRunningDepthMillimeters": 1500,
          "maxRunningDepthMillimeters": 2400,
          "buoyancy": "suspending"
        }
      ]
    }
  ]
}
```

See TD-028 Section 2 for the complete field reference. No field exists for
product photography, logos, or marketing copy — the validator rejects any
unrecognized key.

`lureType` must be one of the codes in `known_lure_types.json`. Adding a
genuinely new lure type is a deliberate one-line addition to that file (and,
for a proper user-facing label, a corresponding addition to
`lib/features/lure_catalog/domain/lure_type_labels.dart`).

## Stable IDs

- IDs are opaque UUID v4 strings, generated once with `new-id` and pasted
  by hand — never computed from manufacturer/model/color text, never
  auto-generated by `validate`/`build` (doing so would break determinism).
- An ID, once published, is permanent. Correcting a name never changes an
  ID; an ID is never reused for a different real-world product.
- `check` and `validate` both run an identity-drift check: if an existing
  ID's manufacturer/model/color identity appears to have changed since the
  last committed `catalog_v1.json`, the build fails unless the record
  explicitly sets `"idReuseAcknowledged": true` — a deliberate,
  human-confirmed escape hatch for a genuine correction.

See TD-028 §4 (Stable Identifier Policy) and §9 (Duplicate Normalization
Rules / identity-drift check) for full detail.

## Content sourcing and licensing

**Allowed:** manufacturer and model names, objective technical
specifications (dimensions, weight, lure type, running depth), and short,
functional manufacturer color names.

**Not included without separately confirmed usage rights:** product
photography, logos, copied marketing/product descriptions, or any
scraped/bulk-imported manufacturer database.

This is the authoritative canonical policy statement, restated here for
convenience:
`docs/specifications/MFS-028-lure-catalog-expansion-and-data-management.md`
§ "Content Sourcing and Licensing". The validator mechanically backs this
up: there is no field in the authoring schema for photography, logos, or
marketing copy, so an attempt to add one fails `validate`/`build`
immediately.

## What this pipeline does

1. **Load** every `*.json` file directly under `assets/lure_catalog/source/`.
2. **Validate** — JSON/schema validity, duplicate model/variant IDs (across
   the whole catalog, not just one file), a model ID never colliding with a
   variant ID, duplicate model names within one manufacturer (normalized),
   duplicate variants within one model (normalized), empty/blank required
   text, unsupported lure types, non-positive or inverted measurements, and
   the identity-drift check described above.
3. **Flatten and sort** — nested `manufacturer → models → variants` becomes
   flat `models[]`/`variants[]` (matching the shape the runtime importer
   consumes), deterministically sorted by (manufacturer, modelName, id) for
   models and (lureModelId, id) for variants.
4. **Write** `assets/lure_catalog/catalog_v1.json`, including a
   `catalogVersion` (read from `assets/lure_catalog/catalog_version.json`,
   set by hand by a developer — this tool never decides version numbering
   on its own) and an informational `generatedAt` timestamp that plays no
   role in any reconciliation decision.

`build` always runs the full `validate` pass first and refuses to write any
output if it fails.

## Refreshing the dataset later

Re-run `python build_catalog.py build` after any source-file change. There
is no scheduled or automatic refresh — this is a deliberate, developer-run
action, exactly like `tools/syke_bathymetry/`'s own precedent.
